# Human API technical design

**Status:** local MVP; review date 26 October 2026. The app is one deployable service, organized into separate modules. Fixed software rules control the workflow. The demo does not use a large language model (LLM) or vector database.

## In plain language

The app saves a question, checks the owner's instructions, checks that the requester can open each file, and then either shows a cited answer or sends the question to a person. These checks are separate: owner consent does not give the requester new access to a file.

**Example:** Alice asks why Project Alpha's timeout changed to 120 seconds. Bob's approved policy allows this question. The app finds ADR-024, a written decision record Alice can read. It says why the change was approved, but does not say if 120 seconds is still needed. The app gives that partial answer with the source and limitation. If the question asks what value is current, two approved documents disagree, so the app asks a human to resolve the conflict.

The word “AI” in the product name describes the intended product direction. Today's answer is created by ordinary code, word matching and fixed templates; it is not generated by a language model. The app's “AI-generated” label means software-produced and distinguishes it from a human reply. For a nontechnical overview and a longer glossary, see the [reader guide](READER_GUIDE.md).

## Terms used below

- **Requester:** the person asking the question.
- **Knowledge owner:** the colleague whose knowledge is being requested.
- **Backup:** the approved person who receives a question that needs human review.
- **Evidence:** a passage from a source file that supports an answer.
- **ACL (access control list):** the list of people allowed to open a file.
- **Lexical search:** finding files by matching words; it does not understand meaning or paraphrases.
- **OBO (“on behalf of”):** a Microsoft sign-in exchange that keeps an API call in the signed-in user's permission context.

## Component boundaries

| Concern | Module | Responsibility |
|---|---|---|
| Identity | `connectors/entra.py` | Check Microsoft work sign-in tokens; OBO helper preserves the signed-in person's permission context. |
| Delegation | `delegation.py` | Active dates, consent, manager approval, topic/audience/project scope. |
| Authorization | `authorization.py` | Check project membership, question visibility, owner policy and file access before retrieval. |
| Question workflow | `workflow.py` | Persistent question state, deadline job, evidence validation, human response, correction approval. |
| Retrieval | `knowledge.py` | Filter to files the requester may read, match words, and apply a narrow hostile-text filter. |
| Graph providers | `connectors/graph_*.py` | Narrow delegated API adapters; not called by enterprise question flow yet. |
| API and audit | `main.py`, `audit.py` | HTTP boundary, role checks, audit records, demo app lifecycle. |
| User interface | `frontend/src/` | Dashboard, question flow, delegation, escalations and governance views. |

The database models persist policy version, question status, deadline jobs, evidence references, validations, human review and audit metadata. The local timeout scanner polls database-backed jobs every three seconds. Atomic state transitions prevent a human response and timeout worker from both winning the same transition in ordinary single-process demo use. Production needs an external worker and database-specific locking/claiming, multi-instance tests, retry observability, and an outbox for notification delivery.

## State and response rules

When a question is submitted, it is saved with a response deadline and a job that survives an app restart. At the deadline—or sooner if an approved out-of-office policy applies—the worker checks the owner's policy and the requester's access. It searches only approved files the requester may read. Clear evidence yields an answer with a citation. Missing or conflicting evidence goes to a human. A disallowed question receives a generic denial. A human answer is labeled as human; a correction must be approved before reuse.

The MVP does not claim a calibrated confidence score. “Supported” means the demo found an authorized document with matching query words; it does not prove that the document logically answers the question. The response composer extracts evidence into a fixed template rather than using an LLM. This avoids generated claims in the local demo, but it also makes answers less flexible.

## Deployment and config

Local use defaults to SQLite and fictional data. `docker-compose.yml` provides a local PostgreSQL option; `make compose` builds the web interface first. The app currently creates tables at startup for the demo; an Alembic migration is included for controlled updates. A production service would also need managed secrets, encrypted connections and storage, monitoring, backups, and an approved data-retention policy.

## Roadmap gates

1. Design review: threat model, owner consent, approved audiences, tenant boundary and retention.
2. Tenant proof: Entra sign-in, OBO Graph search with delegated requester scope, citation ACL revalidation.
3. Teams workflow: use official Teams SDK, register an app/bot, provide public HTTPS endpoint, tenant enablement and user consent; no arbitrary message collection.
4. Quality: blinded human-labeled relevance/entailment set, calibrated abstention, injection/red-team tests.
5. Pilot: opt-in team, non-sensitive docs, human fallback, measurable active-work time, access violations target zero.

## Decisions

- Modular monolith and relational records over microservices or a graph orchestrator: workflow is short and policy-heavy; no demonstrated benefit from multi-agent routing.
- Live delegated retrieval over copied SharePoint indexes for first enterprise proof: reduces ACL drift and avoids owner identity escalation.
- No mailbox content or Teams presence signal: the workflow needs explicit consent and authorized evidence, not silent monitoring.
- Deterministic answer path until evaluation justifies a model.
